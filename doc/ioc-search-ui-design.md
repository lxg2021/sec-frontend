# 情报检索页面界面设计说明

## 1. 页面定位

页面名称：

- 中文：情报检索
- 英文：Intelligence Search

页面地址：

- `/frame/ioc-analysis/ioc-search`

页面目标：

这是一个类似 VirusTotal 的单 IOC 查询页面。用户输入一个 IP、域名、URL、MD5、SHA1 或 SHA256 后，页面立即展示 IOC 情报判断、本地数据定位结果和后续图谱定位入口。

该页面不是案件 IOC 验证工作台，不应该出现明显的 CaseID、案件提取任务、批量预检任务等工作流元素。

## 2. 与现有页面的边界

当前已有页面：

- `/frame/ioc-analysis/ioc-verification`

现有页面职责：

- 从 Attack Workflow 或攻击案件进入。
- 根据 CaseID 加载案件 IOC。
- 支持批量 IOC 预检。
- 支持创建后台验证任务并轮询任务状态。
- 适合案件调查流程，不适合作为独立查询入口。

新页面职责：

- 作为独立情报检索入口。
- 默认只查询一个 IOC。
- 查询逻辑复用现有手动 IOC 查询接口。
- 页面结构参考 VirusTotal：搜索优先、结果聚合、Tab 分区、详情下钻。

## 3. 复用逻辑

新页面必须复用现有手动 IOC 查询逻辑：

```ts
getIocHitDetail({
  tenantId,
  type,
  value,
})
```

对应接口：

```text
POST /sensor/analysis/ioc-hit-detail/get
```

请求核心字段：

```json
{
  "request_id": "...",
  "tenant_id": "public",
  "ioc_type": "ip",
  "value": "8.8.8.8",
  "include_raw_json": true
}
```

查询结果继续使用现有结构：

- `AttackCaseIOCVerificationDetail`
- `AttackCaseIOCVerificationItem`
- `detail_view`
- `final_hit_detail`
- `hit_source_detail`
- `annotation_details`

详情展示可以继续复用：

- `IocVerificationDetailPanel`
- `DetailFieldSections`
- `detailViewSections`

## 4. 新增能力

新页面除了 IOC 情报查询，还需要本地数据定位。

本地定位接口：

```text
POST /sensor/analysis/characteristicposition/page
```

类型映射：

| 输入类型 | IOC 情报查询 | 本地定位 |
|---|---|---|
| IP | `GetIOCHitDetail(ip)` | `IPPosition = 3` |
| Domain | `GetIOCHitDetail(domain)` | `DnsPosition = 2` |
| Hostname | 转成 domain 查询 | `DnsPosition = 2` |
| URL | `GetIOCHitDetail(url)` | 解析 hostname 后走 `DnsPosition = 2` |
| MD5 | `GetIOCHitDetail(md5)` | `FilePosition = 1` |
| SHA1 | `GetIOCHitDetail(sha1)` | 暂不支持本地定位 |
| SHA256 | `GetIOCHitDetail(sha256)` | 暂不支持本地定位 |

图谱定位入口：

- 本地定位结果中解析 `event_type`
- 解析 `event_name`
- 从 `content.UniqueID` 中解析 `unique_id`
- 后续调用 `GraphLocateResult`

## 5. 总体设计原则

页面应该做到：

1. 搜索入口足够强，用户第一眼知道这里是查 IOC 的。
2. 查询结果聚合在首屏，不让用户先看一堆表格。
3. 不再出现案件 IOC 工作台那种左右堆叠布局。
4. 单 IOC 查询优先，批量查询入口降级为次级能力。
5. 视觉要克制、专业、数据导向，避免花哨渐变和大面积装饰。
6. 信息密度要高，但层级要清楚。
7. 所有状态都要明确：恶意、白名单、未知、异常、未命中。

## 7. 首屏布局设计

### 7.1 顶部标题

位置：

- 页面内容区顶部。
- 不做大 Hero 文案。
- 保持运维工具的简洁风格。

内容：

```text
情报检索
输入 IP、域名、URL 或文件 Hash，查询 IOC 情报并定位本地数据。
```

右侧可放：

- 最近查询
- 批量查询
- 帮助说明

但首版可以不放，避免干扰。

### 7.2 搜索框

搜索框是页面第一视觉中心。

布局：

```text
┌──────────────────────────────────────────────────────────────┐
│ [AUTO ▾]  8.8.8.8 / example.com / url / hash...      [查询] │
└──────────────────────────────────────────────────────────────┘
```

设计要求：

- 搜索框宽度占内容区 70%-80%。
- 高度 56px。
- 左侧是类型选择。
- 中间是输入框。
- 右侧是查询按钮。
- 输入值使用等宽字体，便于识别 hash、IP、URL。
- 查询按钮不能过大，避免像营销页。

类型选项：

- AUTO
- IP
- DOMAIN
- URL
- MD5
- SHA1
- SHA256

不建议在独立查询页面默认展示：

- EMAIL
- CERTIFICATE
- HOSTNAME

这些可以后续从高级选项补充。

### 7.3 查询前空状态

查询前不要展示大面积表格空白。

空状态建议：

```text
输入一个 IOC 开始检索
支持 IP、域名、URL、MD5、SHA1、SHA256。
查询会复用现有手动 IOC 验证逻辑，并补充本地数据定位。
```

下面可展示三张轻量说明：

- IOC 情报
- 本地定位
- 图谱定位

## 8. 查询后结果摘要

查询后首屏必须先给结论，不要直接进入详情表。

### 8.1 Verdict 卡片

左侧使用一个判定卡：

```text
┌─────────────────────┐
│ 恶意命中             │
│ 8.8.8.8              │
│ IP                   │
│ 风险分 85 / 置信度 92 │
└─────────────────────┘
```

状态颜色：

| 状态 | 颜色 |
|---|---|
| 恶意命中 | 红色 |
| 白名单 | 绿色 |
| 未知 / 未命中 | 灰色 |
| 查询异常 | 橙红色 |
| 查询中 | 蓝色 |

### 8.2 聚合指标卡

右侧展示 4 个指标：

```text
┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ 白名单        │ │ 本地情报      │ │ 远程情报      │ │ 本地数据      │
│ 未命中        │ │ 命中          │ │ 命中          │ │ 12 条         │
└──────────────┘ └──────────────┘ └──────────────┘ └──────────────┘
```

这 4 个指标足够解释绝大多数查询结果：

- 是否白名单。
- 本地 IOC 库是否命中。
- 远程情报是否命中。
- 本地日志是否出现。

## 9. Tab 设计

查询结果下方使用 Tabs。

推荐 Tab：

1. 概览
2. 情报详情
3. 本地定位
4. 关系数据
5. 原始数据

### 9.1 概览

概览展示“人能直接读懂”的结论。

内容：

- 最终判定。
- 命中来源。
- 风险分。
- 置信度。
- 首次发现时间。
- 最后发现时间。
- 推荐动作。

示例：

```text
当前 IOC 判定为恶意命中。
命中来源为远程威胁情报和本地 IOC 库。
建议查看本地定位命中的主机、进程、DNS 和网络连接记录。
```

### 9.2 情报详情

复用现有 `IocVerificationDetailPanel`。

展示：

- IOC Primary 信息。
- Evidence。
- Sources。
- Relations。
- Whitelist / IOC Entry / Blacklist Indicator 等源表详情。

### 9.3 本地定位

本地定位展示 `CharacteristicPositionPage` 返回的事件。

列表字段建议：

| 字段 | 说明 |
|---|---|
| 事件类型 | `event_name` |
| 时间 | `content.Time` |
| 主机 | `AgentID / Hostname / Computer` |
| 摘要 | 根据事件字段生成简要说明 |
| UniqueID | `content.UniqueID` |
| 操作 | 图谱定位 |

本地定位卡片示例：

```text
NetConnect
WIN-001 powershell.exe -> 8.8.8.8:443
2026-07-07 10:32:18
[图谱定位]
```

### 9.4 关系数据

关系数据不是第一版必须做满。

可以先展示：

- `detail_view.relations`
- `observations`
- 同源 IOC
- 关联域名 / URL / Hash

如果没有数据：

```text
当前 IOC 暂无可展示的关联关系。
```

### 9.5 原始数据

仅给高级用户查看。

展示：

- `verification`
- `detail_view`
- `local_eval_raw_json`
- 本地定位事件原始 `content`

原始数据必须默认折叠或放在最后，不要影响主流程。

## 10. 页面视觉风格

### 10.1 整体风格

关键词：

- 专业
- 克制
- 清晰
- 数据导向
- 类 VirusTotal，但不照抄

避免：

- 大面积渐变。
- 过大的圆角。
- 过多阴影。
- 营销页式 Hero。
- 左右多层卡片套卡片。

### 10.2 色彩

基础色：

- 背景：`#F6F8FB`
- 主文本：`#0F172A`
- 次文本：`#64748B`
- 边框：`#E2E8F0`
- 卡片：`#FFFFFF`

状态色：

- 恶意：`#DC2626`
- 白名单：`#059669`
- 未知：`#64748B`
- 查询中：`#2563EB`
- 异常：`#EA580C`

### 10.3 圆角

建议：

- 页面卡片：8px
- 搜索框：8px
- 按钮：6px
- Badge：999px

不要继续使用 20px、24px、28px 的大圆角作为主视觉，因为这个页面应该更像安全分析工具，不像轻量消费 App。

### 10.4 字体

普通文本：

- `Inter, Microsoft YaHei, sans-serif`

IOC 值、Hash、UniqueID：

- `Consolas, ui-monospace, SFMono-Regular, Menlo, monospace`

## 11. 交互状态

### 11.1 查询中

查询中需要同时展示：

- 查询按钮 loading。
- 摘要区域 skeleton 或 loading。
- 本地定位可以并行 loading。

不建议：

- 整页遮罩。
- 清空页面后只显示一个 spinner。

### 11.2 查询失败

失败区展示：

```text
IOC 查询失败
失败原因...
[重试]
```

本地定位失败不应该影响 IOC 查询结果。

### 11.3 本地定位不支持

例如 SHA1 / SHA256：

```text
当前类型暂不支持本地数据定位。
仍可查看 IOC 情报查询结果。
```

### 11.4 图谱定位

只有当本地事件存在 `UniqueID` 时允许点击。

点击后：

- V1 可以跳转图谱页面。
- 或先弹出“正在定位图谱”。

需要���：

```json
{
  "event_type": 3,
  "event_name": "NetConnect",
  "unique_id": "..."
}
```

## 13. 第一版实现建议

第一版建议只实现这些：

1. 独立 `IocSearchPage`。
2. 顶部单 IOC 搜索框。
3. 查询后摘要卡。
4. Tabs：概览、情报详情、本地定位、原始数据。
5. 情报详情复用现有组件。
6. 本地定位接 `CharacteristicPositionPage`。
7. 图谱定位按钮先接好数据结构，跳转可以第二步做。

第一版不建议做：

1. 批量查询。
2. 最近查询历史。
3. 复杂关系图。
4. CaseID 关联。
5. 任务轮询。

这些会把页面重新拉回“案件工作台”，不符合独立查询页的目标。

## 14. 最终判断

这个页面应该像：

```text
一个安全分析人员打开页面，粘贴一个 IOC，立刻得到结论。
```

而不是：

```text
一个案件处理人员进入工作流，加载 CaseID，批量预检所有 IOC。
```

所以视觉和交互都要围绕“单次查询”和“快速判断”重做。
